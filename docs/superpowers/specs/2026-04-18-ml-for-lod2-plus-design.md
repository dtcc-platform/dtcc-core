# Design: Machine Learning for LoD2+ Building Reconstruction

**Date:** 2026-04-18
**Branch:** `feature/lod2-reconstruction`
**Status:** Design approved — pending implementation plan

## Context

The project currently has a rules-based LoD2 reconstruction pipeline (uncommitted on `feature/lod2-reconstruction`) covering Tier 1 roof types: flat, gabled, hipped. Inputs are classified LiDAR point clouds. Stages: point filtering, normal estimation, RANSAC plane detection, region-growing refinement, plane merging, rule-based roof classification, watertight geometry synthesis, shell validation.

The goal of this design is to introduce machine learning for two purposes:

- **(a) Robustness of the existing LoD2 pipeline** — currently unquantified; no evaluation harness exists, so failure modes are unknown.
- **(b) Broader roof coverage** — extending beyond Tier 1 to Tier 2 types (mansard, shed, gambrel, half-hipped) where rule-based classification becomes unwieldy.

## Strategic framing

The work is split into two tracks:

1. **Track 1 — Evaluation harness (no ML).** Builds the measurement infrastructure that (a) quantifies where the current pipeline succeeds and fails, (b) provides a benchmark against which any ML improvement is judged. Must land before ML work to avoid optimizing blind.
2. **Track 2 — Learned roof-type classifier.** Introduces the first ML component at the classification stage. Lowest-risk insertion point because it is downstream of plane detection (does not require ML over raw geometry) and upstream of geometry synthesis (does not require changes to watertight construction logic).

A third track (imagery-based reconstruction, LoD3 feature detection) is explicitly out of scope and listed in "Follow-on work."

## Baseline assumptions

- **No in-house labeled dataset.** Training data comes from: (i) pseudo-labels generated by the existing rule-based classifier on clean Tier 1 cases, and (ii) public datasets — primarily RoofN3D (~118k buildings with roof-type labels).
- **Machine learning stack: scikit-learn for the first classifier.** The feature-based classifier is small enough that scikit-learn is sufficient and avoids a heavy PyTorch dependency. If a later phase demands a larger model, PyTorch will be added under an optional install group.
- **CPU inference.** The classifier is small enough to run on any CPU in production. Training is also CPU-viable; GPU not required.
- **Rule-based classifier remains the default path.** ML is opt-in via config flag. If the model fails to load or returns low confidence, the pipeline falls back to rules. Non-ML users install no additional dependencies.
- **Ground-truth datasets: user to specify.** RoofN3D is the confirmed primary source for classifier training/validation. Additional sources (Lantmäteriet Swedish data, Building3D, local test sets) to be wired into the eval harness as they are identified.

## Track 1 — Evaluation harness

### Purpose

Turn "we don't know where the pipeline bleeds" into per-building, per-stage measurements with actionable signal.

### Module layout

```
dtcc_core/builder/evaluation/
├── __init__.py
├── dataset.py    # loads (footprint, point_cloud, ground_truth) tuples
├── metrics.py    # individual metric functions
├── runner.py     # drives pipeline across a dataset, collects per-stage timing
└── report.py     # writes CSV, aggregate stats, and failure-gallery VTK exports

sandbox/
└── evaluate_lod2.py  # CLI driver — thin wrapper over runner + report
```

### Dataset convention

A dataset is a directory containing subdirectories per building. Each subdirectory contains:

- `footprint.shp` or `footprint.gpkg` — the 2D footprint polygon
- `points.las` or `points.laz` — classified LiDAR
- `ground_truth.json` — structured ground-truth data (roof type, optional full LoD2 geometry as CityJSON, optional ridge/eave heights)

`dataset.py` exposes:

```python
class EvalDataset:
    def __iter__(self) -> Iterator[EvalSample]: ...
    def __len__(self) -> int: ...

@dataclass
class EvalSample:
    building_id: str
    footprint: Surface
    point_cloud: PointCloud
    ground_truth: GroundTruth
```

### Metrics

Per-building, implemented as pure functions in `metrics.py`:

- **Stage outcome.** For every building, record the terminal outcome of each pipeline stage. `build_lod2_buildings()` already emits one of: `success`, `insufficient_points`, `classification_failed`, `complex_footprint`, `geometry_construction_failed`, `validation_failed`. The harness captures this verbatim and aggregates a breakdown at dataset level. This is the primary signal for "where does it bleed".
- **Per-stage timing** — milliseconds per stage: filter → normals → RANSAC → region-growing → merge → classify → geometry → validate.
- **Roof type accuracy** — predicted `RoofType` vs. ground-truth `RoofType`. Aggregated as a confusion matrix at dataset level.
- **Detection diagnostics** — not only plane count delta, but also:
  - Plane count delta: `abs(detected_planes - expected_planes)`, expected count derived from ground-truth roof type unless explicitly provided.
  - Point coverage ratio: sum of plane inliers divided by filtered-roof-point count. Parallels the `coverage_factor` term used in the rule-based classifier's flat/gabled/hipped confidences.
  - Top-2 area share: area of the two largest detected planes divided by total detected plane area. Parallels the hipped-classification area-ratio rules.
  - Slope symmetry error: for the top two planes by area, absolute difference in tilt angle. Parallels the rule-based symmetric-pair test.
- **Per-surface semantic overlap** — when full ground-truth geometry is available: project predicted surfaces to a shared 2D plane, compute area of overlap per semantic class (roof/wall/ground) divided by area of union. Value in [0, 1].
- **Watertightness** — binary outcome from `shell_validation`. Tracked as a pass-rate.
- **Ridge/eave height error** — absolute error in meters when ground-truth heights are present.
- **Classifier provenance** (introduced in Track 2, but the harness captures it from day one). For every building, record: which classifier path produced the result (`ml`, `rules`, `flat_fallback`) and, when applicable, the reason for fallback from a higher tier. Aggregated into a classifier-source breakdown per dataset.

Aggregate statistics at dataset level:
- Stage outcome breakdown (success rate, failure reason histogram)
- Overall roof-type accuracy (on the subset that reached `success`)
- Confusion matrix
- Detection diagnostic distributions (median, p95 for each)
- Watertightness pass rate
- Mean per-surface semantic overlap
- Per-stage timing distribution (min/median/p95/max)
- Classifier-source breakdown (from Track 2 onward)

### Failure gallery

For any building that fails any threshold (configurable: e.g., semantic overlap < 0.7, plane count delta > 2, non-watertight), export a VTK file reusing the existing `sandbox/export_vtk.py` logic. Enables visual inspection of failures without re-running the pipeline.

### Acceptance for Track 1

- Runs on at least one real dataset end-to-end
- Produces a CSV with all metrics for every building
- Produces aggregate stats written to console and a summary JSON
- Failure gallery exported for threshold-crossing buildings
- Runs in under 10 minutes for a dataset of 1,000 buildings

## Track 2 — Learned roof-type classifier

### Purpose

Replace the rule-based classifier with a learned function that (a) matches rule-based accuracy on Tier 1 and (b) extends cleanly to Tier 2 roof types without growing the rule codebase.

### Model shape

Feature-based classifier. The model consumes a small fixed-length feature vector derived from the `List[RoofPlane]` produced by existing detection. Candidate architectures in order of preference:

1. **Gradient-boosted decision trees** (scikit-learn `GradientBoostingClassifier` or `HistGradientBoostingClassifier`) — strong tabular baseline, interpretable feature importances, robust to small data.
2. **Small MLP** (scikit-learn `MLPClassifier`) — if tree-based model shows signs of underfitting on larger Tier 2 data.

Both are sub-megabyte on disk. Both run in sub-millisecond on CPU.

### Feature engineering

Features extracted per building from `List[RoofPlane]` plus the upstream filtered roof point cloud. The feature set deliberately mirrors the quantities the existing rule-based classifier relies on, to ensure the ML model has at least the same information in hand.

**Per-plane aggregates** (min/max/mean/stddev across planes, where meaningful):
- Tilt angle (angle between normal and vertical)
- Area (absolute and as fraction of total detected plane area)
- Centroid Z expressed **relative** to the minimum plane centroid Z — measures eave-to-ridge structure, not world altitude
- Inlier count

**Ordered area-share features** (top-N planes by area, N = 3):
- `area_share_1`, `area_share_2`, `area_share_3` — each plane's area as a fraction of total detected plane area, in descending order
- Rationale: the rule-based hipped classifier requires the top two planes to each clear `hip_main_area_ratio`. Aggregated mean/stddev does not preserve this structure; ordered shares do.

**Coverage features:**
- `coverage_ratio = sum(plane_inliers) / filtered_roof_point_count` — parallels the `coverage_factor` that appears in every confidence term of the rule-based classifier
- `residual_ratio = 1 - coverage_ratio` — fraction of filtered points not explained by any detected plane; proxy for gabled-to-hipped upgrade and complexity signal

**Structural features** (derived, fixed-length):
- Count of near-horizontal planes (tilt < flat_angle_threshold), normalized by detected plane count
- Count of near-symmetric plane pairs (equal tilt, opposite azimuth), normalized by possible pair count `C(n, 2)`
- Count of plane pairs with high azimuth opposition (opposition score > 0.85), normalized by possible pair count
- Azimuth spread (circular standard deviation)
- Relative ridge height: `(max plane centroid Z − min plane centroid Z) / footprint diagonal`
- Footprint compactness: `perimeter² / area`
- Total detected roof area / footprint area

**Pairwise aggregates** over top-N planes, N = 3 (to keep feature length bounded):
- For each ordered pair (i, j) with i < j: angle between normals, azimuth opposition score, centroid distance normalized by footprint diagonal

Features explicitly **not** included:
- Raw plane count as a standalone feature — already reflected through normalized structural features; including it raw risks the model memorizing detector output rather than geometric structure
- Raw world-frame centroid Z — replaced with relative heights
- Un-normalized pair counts — replaced with rate features

Resulting feature vector length is fixed regardless of how many planes the detection stage produced. Missing planes (when detected count < N) contribute zero-padded entries and a corresponding presence-mask feature.

### Integration with existing pipeline

`RoofDetectionConfig` gains three fields:

```python
use_ml_classifier: bool = False
ml_model_path: Optional[str] = None
ml_min_confidence: float = 0.6
```

`ClassificationResult` gains two fields to support provenance tracking end-to-end:

```python
@dataclass
class ClassificationResult:
    # existing fields: roof_type, confidence, roof_planes, ridge_line, eave_height, ridge_height
    classifier_source: Literal["ml", "rules", "flat_fallback"] = "rules"
    classifier_fallback_reason: Optional[str] = None    # "ml_low_confidence", "ml_load_failed", etc.
```

**Naming note — avoid collision with pipeline-level fallback:** the name `fallback_reason` is already used in `building.attributes["fallback_reason"]` to mean **terminal pipeline failure** (`insufficient_points`, `classification_failed`, `complex_footprint`, `geometry_construction_failed`, `validation_failed`). To keep the two concepts cleanly separated, the classifier-dispatch fallback uses the distinct name `classifier_fallback_reason`. The eval harness already exposes the pipeline-level one as `fallback_reason_attr` in `BuildingResult`; Track 2 adds `classifier_source` and `classifier_fallback_reason` to `BuildingResult` alongside it.

`roof_classification.classify_roof()` gains a dispatch at the top:

```python
def classify_roof(planes, footprint, config):
    if config.use_ml_classifier and config.ml_model_path:
        try:
            ml_result = _classify_with_ml(planes, footprint, config)
            if ml_result.confidence >= config.ml_min_confidence:
                ml_result.classifier_source = "ml"
                return ml_result
            classifier_fallback_reason = "ml_low_confidence"
        except (ImportError, FileNotFoundError, ModelLoadError) as e:
            classifier_fallback_reason = f"ml_load_failed:{type(e).__name__}"
    else:
        classifier_fallback_reason = None
    result = _classify_with_rules(planes, footprint, config)
    result.classifier_source = "rules"
    result.classifier_fallback_reason = classifier_fallback_reason
    return result
```

Provenance fields propagate through `buildings.py` into the attribute layer already used for `result_status`, so the eval harness can read them without touching the pipeline internals. This is load-bearing — without provenance it is trivially possible for a broken ML model to look safe behind the fallback chain while contributing zero actual wins.

No other changes required downstream — the existing `ClassificationResult` consumers are field-additive-compatible.

### Training data strategy

**Phase 1 — Parity via pseudo-labels.**
Run the rule-based classifier over a clean LiDAR dataset (buildings where RANSAC converges with high confidence and no rule-based ambiguity). Use rule outputs as training labels for the ML classifier. Goal: demonstrate the ML infra works end-to-end and reaches rule-based accuracy. No accuracy gain expected at this phase.

**Phase 2 — Tier 2 via public data.**
Train on RoofN3D (118k buildings, labeled). Extend `RoofType` enum to include `mansard`, `shed`, `gambrel`, `half_hipped`. Measure accuracy gain on the eval harness. This is where ML is expected to earn its place.

### Testing requirements

The dispatch chain introduces new branches that must have explicit test coverage:

- Model-load failure path (missing file, corrupt file, incompatible scikit-learn version) falls back to rules with `classifier_fallback_reason="ml_load_failed:..."`.
- Low-confidence ML prediction (confidence below threshold) falls back to rules with `classifier_fallback_reason="ml_low_confidence"`.
- High-confidence ML prediction is returned with `classifier_source="ml"` and propagates into building attributes.
- `use_ml_classifier=False` path unchanged — regression test against the existing rule-based outputs on fixtures.
- Parity-mode test: ML classifier trained on pseudo-labels produces the same `RoofType` as rules on a held-out subset at a documented rate (≥95%).

### Dataset transfer risk

RoofN3D provides labeled training data, but the label definitions and the distribution of plane-detection features in RoofN3D will not exactly match what `dtcc-core`'s RANSAC + region-growing pipeline produces on our target datasets. A model trained only on RoofN3D-derived features may degrade when applied to features from our own pipeline.

Mitigation:
- Run the dtcc-core plane-detection stage on RoofN3D point clouds (rather than consuming RoofN3D's own plane annotations, if present) so training features are produced by the same code path as inference features.
- Keep a local held-out test set for final evaluation — the eval harness on real data is the only metric that matters.
- If distribution mismatch remains a problem, consider fine-tuning on pseudo-labels from our own pipeline after RoofN3D pretraining.

### Acceptance for Track 2

**Phase 1:**
- Training pipeline runs end-to-end on pseudo-labels
- Model serializes and loads correctly
- ML classifier reaches ≥95% agreement with rule-based classifier on held-out Tier 1 data
- Eval harness runs with `use_ml_classifier=True` and produces a classifier-source breakdown showing non-trivial ML usage (not 100% fallback)
- All test cases in "Testing requirements" pass

**Phase 2:**
- RoofN3D loader produces training-ready data, features computed via dtcc-core's own plane-detection stage
- Classifier extended to Tier 2 types (4 new types)
- Eval harness shows accuracy improvement on a Tier-2-inclusive test set compared to Phase 1 classifier AND compared to rule-based baseline
- Confusion matrix published per roof type
- Dataset-transfer risk explicitly measured: report ML accuracy on (a) RoofN3D held-out, (b) local test set — gap between them is the transfer penalty

## Rollout sequencing

1. **Commit the rule-based LoD2 baseline first.** The current uncommitted work on `feature/lod2-reconstruction` is the frozen baseline for everything that follows. A benchmark harness without a frozen, versioned baseline is not reproducible. This step lands before the eval harness. Existing tests for the rule-based pipeline must pass.
2. **Eval harness (Track 1).** Lands on top of the committed baseline. Produces the initial numbers against which every later improvement is measured.
3. **Classifier Phase 1 (Track 2, parity).** Proves the ML plumbing with pseudo-labels from the committed baseline. Not expected to win on accuracy; expected to match and to demonstrate the dispatch chain behaves correctly.
4. **Classifier Phase 2 (Track 2, Tier 2 expansion).** RoofN3D training, Tier 2 type extension, eval-harness comparison. This is where ML is expected to earn its place.
5. **Follow-on** — see below.

## Follow-on work (out of scope for this spec)

The following are noted as future directions but are not covered by this design. Each warrants its own spec when prioritized.

### Gemma 4 integration

Gemma 4 was released 2026-04-02 as a natively-multimodal open model family (2B / 4B / 26B MoE / 31B Dense) with strong image understanding, object detection, and structured-output capabilities. It does not consume 3D point clouds natively, but can consume a rendered top-down image of the point cloud.

Three potential insertion points for a future spec:

- **Zero-shot baseline in the eval harness.** Render each roof point cloud to a top-down orthographic image, feed to Gemma 4 E2B, parse the predicted roof type. Produces a comparison column in the eval harness CSV — no training required. Useful both as a sanity check and as a continuously-updated reference point as the learned classifier evolves.
- **Last-resort fallback in the classifier dispatch.** When the small learned classifier returns confidence below threshold, fall back to Gemma 4 before falling back to rules. Catches unusual roof shapes the learned classifier wasn't trained on.
- **LoD3 feature detection** (windows, doors, dormers, chimneys). Gemma 4's "pointing" capability returns image coordinates for requested features. Most natural fit for eventual LoD3 facade articulation work. Requires imagery input (aerial or street-level), which is itself a prerequisite.

### Other follow-on tracks

- **Raw-point-cloud classifier (PointNet++ / RandLA-Net / KPConv class of models).** If the feature-based classifier hits a ceiling exposed by the eval harness — particularly on Tier 2+ buildings with noisy or sparse point clouds — upgrade the classifier to consume points directly. Adds PyTorch dependency and introduces GPU-preferred training. Justified only once evidence demands it.
- **Roof topology graph prediction for compound roofs.** Tier 3 compound shapes (L/T/U-shaped, cross-gabled) need a model that predicts ridge and eave lines as a connected graph (approaches in the lineage of City3D, Roofline-Net). Geometry synthesis consumes the graph and builds the watertight shell. This is the path to compound-roof coverage and is research-grade complexity.
- **Learned normal estimation.** If the eval harness identifies noisy normals as a bottleneck, replace Open3D's KNN-PCA normal estimation with a learned normal estimator. Plug-in replacement at one pipeline stage.
- **Imagery-based reconstruction** (the "option D" from initial brainstorming). Aerial or satellite imagery as a secondary input for buildings with sparse LiDAR. Benefits from Gemma 4 or a dedicated vision model; needs a full new input pipeline and calibration.

## Non-goals

- Replacing the deterministic geometry synthesis with ML. Watertight construction stays rule-based.
- Replacing RANSAC/region-growing with ML in this spec (deferred; may surface as follow-on if eval harness demands it).
- Supporting LoD3 features (openings, dormers, textures) in this spec.
- GPU-required training or inference paths.

## Open questions (for implementation plan)

1. **Ground truth dataset access.** Which datasets does the user actually have with full LoD2 ground truth? RoofN3D covers classification; full geometry benchmarks need something like Helsinki3D, Vienna, Building3D, or a Swedish source.
2. **Failure threshold configuration.** What specific thresholds trigger VTK export in the failure gallery? Sensible defaults will be proposed in the implementation plan.
3. **Commit boundaries for the rule-based baseline.** The uncommitted LoD2 work is one branch's worth of changes touching many files (buildings.py +234 lines, proto schema changes, new modules, many tests). The implementation plan should propose a commit breakdown (baseline geometry builders, proto/model changes, tests, sandbox scripts) so the baseline lands as a coherent history rather than a single monolithic commit.
