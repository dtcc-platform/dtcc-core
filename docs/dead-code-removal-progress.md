# C++ Dead-Code Audit Progress

Last updated: 2026-07-23  
Working branch: `dev/deadCodeRemoval`

## Goal

Audit the C++ implementation in `dtcc_core/cpp`, then incrementally remove
legacy code that is not reachable from the supported Python API, pybind11
bindings, tests, or active C++ execution paths. The audit includes first-party
headers under `cpp/include`, vendored material under `cpp/external`, CMake
configuration, bindings, tests, examples, and related documentation.

The pybind11 module entry point is
`dtcc_core/cpp/dtcc_builder.cpp::PYBIND11_MODULE(_dtcc_builder, m)`.

## Agreed Approach

### Reachability model

The audit uses two related graphs:

1. **Compilation graph**: files included by each supported CMake
   configuration.
2. **Semantic graph**: functions, methods, types, and data reachable from the
   module initializer, live pybind11 registrations, active C++ calls, and
   supported optional configurations.

A pybind11 registration is a reachability root even when the Python package
does not currently call it. Such code is classified as `BINDING_ONLY` until an
explicit compatibility decision permits removal of the binding.

### Classification

Every reviewed component should be assigned one of these states:

- `ACTIVE`: reachable from a supported production path.
- `BINDING_ONLY`: reachable only because it is exposed by pybind11.
- `CONFIG_ONLY`: reachable only in an optional supported build configuration.
- `REGENERATION_INPUT`: used to reproduce generated source code.
- `VENDORED_SNAPSHOT`: retained as part of an upstream dependency snapshot.
- `UNREACHABLE`: outside all supported reachability roots.
- `UNKNOWN_NEEDS_REVIEW`: insufficient evidence for safe removal.

### Evidence and tools

- CMake `compile_commands.json`, compiler dependency files, and
  `ninja -t deps` for configuration-specific include closure.
- Clang AST/LibTooling analysis for declarations and reference edges.
- Debug builds and `nm -C` to corroborate which symbols are emitted.
- Compiler warnings and static analyzers as candidate generators, not as sole
  proof of dead code.
- Coverage as execution evidence, not as proof that unexecuted code is dead.
- Build, extension import, and focused tests after each change.

### Commit discipline

Each commit must build and import independently. Checking out any individual
commit should produce a compilable C++ extension and a working import of
`_dtcc_builder`; a commit must not rely on a later commit to repair broken
includes, bindings, or CMake configuration. Focused validation is required per
commit, with the full supported CI matrix required before merging a PR.

## Important Audit Findings

- The extension currently has one first-party C++ translation unit,
  `dtcc_core/cpp/dtcc_builder.cpp`.
- The older FEM/AMGCL elasticity stack remains active through the Python
  volume-meshing fallback. It is not dead code while that fallback is
  supported.
- Current tests largely exercise the TetGen path and do not adequately protect
  the fallback volume mesher. A fallback contract test should precede changes
  to that stack.
- Optional Triangle support is configuration-specific and must be included in
  the validation matrix.
- Eigen and AMGCL should be treated as atomic vendored snapshots unless the
  project deliberately adopts a different dependency policy. Individual
  headers should not be pruned using one platform's include closure.
- UFL files and form-generation scripts are regeneration inputs, not runtime
  dead code.
- The compatibility status of the private-looking `_dtcc_builder` module is
  not yet defined. Package-unused bindings must remain `BINDING_ONLY` until
  that decision is made.

## Proposed Reachability Audit Tool

Status: **Designed; not yet implemented**

The proposed entry point is `scripts/audit_cpp_reachability.py`. It should use
only the Python standard library for orchestration and reporting, invoking
CMake, Ninja, and Clang as external tools. More complex extractors may be split
into a small `scripts/cpp_reachability/` package as the implementation grows.

### Inputs

- Tracked-file inventory from Git for `dtcc_core/cpp/include`,
  `dtcc_core/cpp/external`, C++ sources, CMake files, Python callers, and tests.
- `compile_commands.json` generated by CMake for each supported profile.
- Compiler dependency output for the exact include closure of each profile.
- Clang AST output for first-party declarations and semantic reference edges.
- Python AST output identifying production and test references to
  `_dtcc_builder` exports.
- A reviewed configuration file containing supported profiles, dynamic Python
  references, vendored snapshots, regeneration inputs, and other explicit keep
  rules. Every manual rule must include a rationale.

Initial local profiles:

- `default`: Triangle disabled and normal Boost discovery.
- `no_boost`: Triangle disabled and Boost discovery explicitly disabled.
- `triangle`: vendored Triangle enabled.

Linux, macOS, and Windows results should eventually be merged in CI. A node is
not a deletion candidate unless it is unreachable in the union of all
supported profile/platform manifests.

### Graph model

The canonical graph should contain typed nodes for files, C++ symbols, Python
callers, pybind11 exports, build targets, configurations, and collapsed vendor
packages. It should contain typed edges such as:

- `contains`
- `includes`
- `binds`
- `calls`
- `constructs`
- `references`
- `python_calls`
- `enabled_by`
- `generated_from`

Every edge must record its evidence source and applicable profiles. Symbol IDs
must be based on repository-relative paths and qualified signatures rather
than transient AST addresses or absolute paths.

The module initializer and every live pybind11 registration are conservative
roots. Virtual dispatch, function pointers, callbacks, and template
instantiations must be handled conservatively: uncertainty keeps code rather
than classifying it as dead.

### Reproducible outputs

The default output directory should be `build/cpp-reachability/` and contain:

- `manifest.json`: canonical, stable-sorted nodes, edges, profiles,
  classifications, and reasons.
- `run-metadata.json`: non-semantic environment details such as compiler
  version, platform, and Git revision.
- `summary.md`: counts and human-reviewable candidate tables.
- `graphs/files.dot`: first-party include graph with vendor packages collapsed.
- `graphs/api.dot`: Python caller to pybind11 export to C++ symbol chains.
- `graphs/symbols.dot`: first-party call/reference graph.
- `graphs/dead-islands.dot`: disconnected candidate components.

Graphviz rendering to SVG should be optional. DOT generation must work without
Graphviz, while `--render` may create SVG files when `dot` is installed. Full
per-header vendor expansion should be opt-in because the default dependency
graph would otherwise be too large to review.

The semantic manifest must exclude timestamps and absolute machine paths so
that repeated runs for the same source and profiles are byte-for-byte stable.
Volatile environment data belongs only in `run-metadata.json`.

### Proposed command interface

```text
python scripts/audit_cpp_reachability.py run \
  --profiles default,no_boost,triangle \
  --build-root build/cpp-reachability

python scripts/audit_cpp_reachability.py explain \
  --manifest build/cpp-reachability/manifest.json \
  --node <stable-node-id>

python scripts/audit_cpp_reachability.py graph \
  --manifest build/cpp-reachability/manifest.json \
  --view api --render

python scripts/audit_cpp_reachability.py check \
  --manifest build/cpp-reachability/manifest.json \
  --baseline docs/cpp-audit/reachability-baseline.json
```

`explain` should print one or more shortest evidence chains from a root to a
selected node. This is the primary answer to “why is this code retained?” and
is more useful during review than searching a large graph manually.

### Implementation boundaries

1. File inventory, configuration profiles, compiler include closure, normalized
   JSON manifest, and file-level DOT graph.
2. Python caller and pybind11 export inventory, plus the API-chain graph.
3. Clang AST symbol/reference extraction and conservative reachability closure.
4. Baseline comparison, `explain`, CI artifact generation, and cross-platform
   manifest union.

Each boundary should be a separate buildable and testable commit. The audit
tool must not delete source files; it only reports candidates and evidence.

### Acceptance criteria

- Two runs for the same source, toolchain, and profiles produce identical
  `manifest.json` files.
- All paths in the semantic manifest are repository-relative.
- Every retained first-party node has a root reason or a reviewed keep rule.
- Every unreachable candidate includes the profiles checked and its evidence
  limitations.
- The active fallback chain from Python volume meshing through
  `VolumeMeshBuilder`, elastic smoothing, and AMGCL is visible.
- Triangle-only nodes are classified as configuration-specific.
- Binding-only paths can be distinguished from production Python callers.
- Unit tests use small fixtures and do not require a full C++ build; one
  integration test exercises the actual repository translation unit.

### Phase 4 removal evidence report

This section justifies every removal individually so the series can be
reviewed without reading diffs. For each item it states what the code did, why
it was classified `UNREACHABLE`, and the evidence behind that classification.

**How to read the evidence.** The reachability roots are: the pybind11 module
initializer and every live registration in `dtcc_core/cpp/dtcc_builder.cpp`
(the sole C++ translation unit), Python code under `dtcc_core/`, and the test
suite. A C++ symbol was classified dead only when a repository-wide search
found no reference to it outside its own definition, its own documentation
comment, commented-out code, or another symbol in the same removal set. Every
claim below can be re-checked against the pre-removal tree with
`git grep -n "<name>" <commit>^` (e.g. `git grep -n point_coverage a6fa0a0^`).
Each commit was additionally validated by a fresh compile — a genuinely
referenced C++ symbol cannot be removed without breaking the build — plus
extension import, the 48-name export guard test, and the builder test suite.
An independent verification pass re-derived the call-site analysis for every
item before it was committed.
